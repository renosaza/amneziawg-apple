# Architecture

The target macOS architecture keeps tunnel lifecycle and UI state in `TunnelsManager`; each NetworkExtension session owns its adapter and `utun`. Routing remains inside NetworkExtension settings, including excluded routes. No external routing process is part of the design.

For the intended three-tunnel topology:

| Destination | Owner |
| --- | --- |
| `10.25.0.0/24` | CM tunnel |
| `10.1.1.2/32` | pdkkfc tunnel |
| `192.168.31.0/24` | physical interface |
| `77.105.177.18/32` | physical interface |
| `95.154.96.103/32` | physical interface |
| all other IPv4/IPv6 traffic | sticky-indigo full tunnel |

The two corporate endpoint routes must stay on the physical uplink while sticky-indigo is active. `ExcludeIPs` expresses this policy on the full-tunnel profile and must only become NetworkExtension excluded routes; it must not become a backend `allowed_ip`.

## Current limitations

Split DNS is deferred. At the recorded Amnezia base, any profile with DNS servers installs `matchDomains = [""]`, making it the global resolver. Multiple active DNS-owning tunnels therefore have no validated DNS isolation.

Endpoint bypasses generated by a tunnel cover that tunnel's resolved peers. They do not provide cross-profile hostname ownership: `ExcludeIPs` is CIDR-only, so a corporate hostname that later resolves to a different address needs an explicit routing-policy update and runtime route verification before it can be considered safe from a concurrent full tunnel.

See [Decision 0001](decisions/0001-macos-multitunnel-routing.md) for activation and conflict rules.
